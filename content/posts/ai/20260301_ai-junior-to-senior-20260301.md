# 從 Junior 到 Senior：開發者必須完成的思維與技術轉型

許多工作 2-3 年的工程師常感到困惑：程式碼寫得越來越順手，但總覺得離「資深」還有一段距離。這段距離並非單純的技術深度，而是思維模式的轉變。資深工程師看重的是商業價值與系統穩定，而不僅是新技術。

## 從「實作功能」到「設計系統」

Junior 工程師的目標通常是「完成任務」，專注於將需求轉化為可執行的程式碼。Senior 工程師則會思考「這個功能如何融入現有系統？未來如何擴充？」。這並非鼓勵過度設計，而是要培養系統思維。

過度設計（Over-engineering）和設計不足（Under-engineering）都是陷阱。過度設計會增加不必要的複雜性，讓系統難以維護；設計不足則會導致系統僵化，難以應對變化。

**情境分析：微服務的迷思**

微服務架構近年來非常流行，但許多團隊盲目追求微服務，導致系統複雜度暴增。一個常見的錯誤是將原本簡單的單體應用拆分成數十個微服務，每個微服務只負責極小的功能，服務間的通訊成本遠遠超過了服務本身的價值。

在決定採用微服務之前，務必仔細評估：

*   **團隊規模：** 微服務需要獨立的團隊負責維護，小團隊難以勝任。
*   **業務複雜度：** 簡單的業務場景不需要微服務。
*   **部署與維運能力：** 微服務的部署與維運比單體應用複雜得多。

如果你的團隊規模不大，業務邏輯也不複雜，那麼單體應用可能更適合。重要的是選擇最適合的架構，而不是盲目追隨潮流。

## 從「修復 Bug」到「管理複雜度」

Junior 工程師的日常工作可能是修復 Bug。Senior 工程師則會思考如何從源頭減少 Bug 的產生，並提高程式碼的可維護性。

可維護性是衡量程式碼品質的重要指標。高耦合度、低內聚性的程式碼難以理解和修改，容易產生 Bug。單元測試是提高程式碼可維護性的有效手段，但並非萬能。過度追求單元測試覆蓋率，反而會增加維護成本。

技術債是另一個需要關注的問題。為了趕進度，我們可能會採用一些「dirty hacks」，這些 hacks 會在未來帶來麻煩。Senior 工程師會意識到技術債的存在，並主動償還。

**程式碼範例：錯誤處理**

以下是一個 Junior 工程師常見的錯誤處理方式（Python）：

```python
def process_data(data):
    try:
        result = int(data) * 2
        return result
    except:
        return None  # 錯誤處理很粗糙
```

這種寫法簡單直接，但存在問題：

*   無法區分錯誤類型，所有錯誤都返回 `None`。
*   沒有記錄錯誤資訊，難以追蹤問題。

以下是一個 Senior 工程師的寫法：

```python
import logging

def process_data(data):
    try:
        result = int(data) * 2
        return result
    except ValueError as e:
        logging.error(f"Invalid data format: {data}, error: {e}")
        return None
    except Exception as e:
        logging.exception(f"Unexpected error processing data: {data}") # 記錄完整的堆疊追蹤
        return None
```

這個版本改進了以下方面：

*   區分了 `ValueError` 和其他異常。
*   使用 `logging` 記錄錯誤資訊，方便追蹤問題。
*   針對未預期的錯誤，記錄完整的堆疊追蹤資訊。

## 從「個人貢獻」到「技術影響力」

Junior 工程師主要關注自己的任務，Senior 工程師則會思考如何提升整個團隊的效率。

Code Review 是提升團隊程式碼品質的重要手段。Senior 工程師會積極參與 Code Review，不僅僅是檢查程式碼是否符合規範，更重要的是提出建設性的意見，幫助其他工程師成長。

技術決策也是 Senior 工程師的重要職責。在做出技術決策時，需要權衡各種因素，例如：成本、風險、可維護性、擴充性。

**程式碼範例：策略模式**

假設我們需要根據不同的支付方式計算費用。以下是一個 Junior 工程師常見的寫法（JavaScript）：

```javascript
function calculateFee(paymentMethod, amount) {
  if (paymentMethod === 'creditCard') {
    return amount * 0.03 + 1; // 信用卡手續費
  } else if (paymentMethod === 'paypal') {
    return amount * 0.04 + 0.5; // PayPal 手續費
  } else if (paymentMethod === 'bankTransfer') {
    return amount * 0.01; // 銀行轉帳手續費
  } else {
    return amount; // 其他支付方式
  }
}
```

這種寫法簡單直觀，但存在問題：

*   可讀性差，大量的 `if-else` 語句難以理解。
*   擴充性差，新增支付方式需要修改 `calculateFee` 函數。
*   違反了開閉原則（Open/Closed Principle）。

以下是一個 Senior 工程師的寫法：

```javascript
class PaymentStrategy {
  calculate(amount) {
    throw new Error("Method 'calculate' must be implemented.");
  }
}

class CreditCardStrategy extends PaymentStrategy {
  calculate(amount) {
    return amount * 0.03 + 1;
  }
}

class PaypalStrategy extends PaymentStrategy {
  calculate(amount) {
    return amount * 0.04 + 0.5;
  }
}

class BankTransferStrategy extends PaymentStrategy {
  calculate(amount) {
    return amount * 0.01;
  }
}

class PaymentCalculator {
  constructor(strategy) {
    this.strategy = strategy;
  }

  calculateFee(amount) {
    return this.strategy.calculate(amount);
  }
}

// 使用方式
const creditCardCalculator = new PaymentCalculator(new CreditCardStrategy());
const fee = creditCardCalculator.calculateFee(100); // 計算信用卡手續費
```

這個版本使用了策略模式，將不同的支付方式封裝成獨立的類別。這種寫法具有以下優點：

*   可讀性好，每個類別只負責計算一種支付方式的費用。
*   擴充性好，新增支付方式只需要新增一個類別，不需要修改現有程式碼。
*   符合開閉原則。

策略模式是一種常見的設計模式，可以有效地降低程式碼的複雜度，提高程式碼的可維護性和擴充性。

總之，從 Junior 到 Senior 的轉變，不僅僅是技術能力的提升，更重要的是思維模式的轉變。要從關注個人貢獻轉向關注團隊效率，從關注功能實現轉向關注系統穩定。只有這樣，才能真正成為一名資深的工程師。
