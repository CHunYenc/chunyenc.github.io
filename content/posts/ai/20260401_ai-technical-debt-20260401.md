# 技術債不是髒話：務實工程師的債務管理策略

技術債，這三個字經常在開發團隊中引起焦慮。但身為一個經歷過多次大型系統重寫的架構師，我想說：技術債本身不是問題，問題在於你如何管理它。如同財務債務，適度的技術債可以加速產品上市，但失控的技術債則會拖垮整個專案。

## 技術債的分類：認清你的債務

技術債並非鐵板一塊，區分不同類型的債務至關重要：

*   **刻意的 vs 無意的：** 刻意的技術債是為了快速交付而有意識地做出的妥協，例如為了趕上截止日期而犧牲了程式碼品質。無意的技術債則是在缺乏經驗或對問題理解不足的情況下產生的，例如使用了不適合的設計模式。
*   **短期的 vs 長期的：** 短期的技術債影響範圍小，容易修復，例如一個小小的程式碼風格不一致。長期的技術債則會深入系統架構，影響擴充性、可維護性，甚至安全性。

理解技術債的類型，才能制定更有效的償還策略。

## 量化與溝通：讓數字說話

身為工程師，我們習慣用技術術語溝通，但面對非技術主管，這種方式往往行不通。要讓他們理解技術債的成本與風險，必須將其量化：

*   **開發速度：** 統計完成相同功能的開發時間，比較技術債累積前後的差異。例如，「由於模組 A 的高耦合度，現在開發一個新功能需要 3 倍的時間」。
*   **錯誤率：** 追蹤由技術債引起的錯誤數量，以及修復這些錯誤所需的時間。例如，「過去三個月，有 20% 的錯誤是由於模組 B 的複雜邏輯造成的」。
*   **維護成本：** 估算維護和修改現有程式碼的成本，包括除錯、測試和部署。例如，「由於模組 C 的缺乏單元測試，每次部署都需要額外 2 天的測試時間」。

將這些數字呈現給非技術主管，他們才能更清楚地理解技術債的影響，並支持你的重構計劃。

## 償還策略：持續投資，避免革命

償還技術債沒有一蹴可幾的方案，以下是一些務實的策略：

*   **Boy Scout Rule：** 每次修改程式碼時，都盡力讓它比你接手時更好一點。這是一種持續改善的策略，可以逐步減少技術債。
*   **策略性重構：** 選擇影響範圍廣、風險高的模組進行重構。這需要仔細的規劃和測試，但可以顯著提高系統的整體品質。
*   **「大爆炸重寫」：** 這是最危險的策略，通常是陷阱。

### 大爆炸重寫 vs 漸進式重構：一個情境比較

假設我們有一個電商網站，負責處理訂單的模組因為早期設計不良，耦合度極高，導致新增支付方式非常困難。

**大爆炸重寫：** 團隊決定完全重寫訂單模組，預計耗時 6 個月。在這段時間內，現有系統的維護成本仍然很高，而且重寫的風險極大，可能延遲交付，甚至引入新的錯誤。

**漸進式重構：** 團隊首先將訂單模組拆解成更小的、獨立的元件，例如訂單驗證、支付處理、庫存管理等。然後，逐步重構每個元件，並確保它們之間的介面清晰明確。這個過程可能需要 12 個月，但風險較低，並且可以在重構過程中持續交付新功能。

**結論：** 在大多數情況下，漸進式重構是更明智的選擇。它允許你逐步降低技術債，同時保持系統的可用性和可維護性。

### 程式碼範例：重構前後的對比

以下是一個簡化的例子，展示了重構前後的程式碼差異。

**技術債累積後難以修改的版本 (JavaScript):**

```javascript
function processOrder(order, paymentMethod) {
  if (paymentMethod === 'creditCard') {
    // 信用卡支付邏輯，包含大量的重複程式碼
    console.log('Processing credit card payment...');
    // ... 複雜的信用卡支付流程 ...
  } else if (paymentMethod === 'paypal') {
    // PayPal 支付邏輯，與信用卡支付邏輯高度耦合
    console.log('Processing PayPal payment...');
    // ... 複雜的 PayPal 支付流程 ...
  } else if (paymentMethod === 'applePay') {
    // Apple Pay 支付邏輯，程式碼結構混亂
    console.log('Processing Apple Pay payment...');
    // ... 複雜的 Apple Pay 支付流程 ...
  } else {
    console.log('Invalid payment method.');
  }

  // ... 其他訂單處理邏輯 ...
}
```

**套用策略性重構後清晰可維護的版本 (JavaScript):**

```javascript
class PaymentProcessor {
  processPayment(order) {
    throw new Error('Method not implemented.');
  }
}

class CreditCardProcessor extends PaymentProcessor {
  processPayment(order) {
    console.log('Processing credit card payment...');
    // ... 信用卡支付邏輯 ...
  }
}

class PayPalProcessor extends PaymentProcessor {
  processPayment(order) {
    console.log('Processing PayPal payment...');
    // ... PayPal 支付邏輯 ...
  }
}

class ApplePayProcessor extends PaymentProcessor {
  processPayment(order) {
    console.log('Processing Apple Pay payment...');
    // ... Apple Pay 支付邏輯 ...
  }
}

function processOrder(order, paymentMethod) {
  let processor;
  switch (paymentMethod) {
    case 'creditCard':
      processor = new CreditCardProcessor();
      break;
    case 'paypal':
      processor = new PayPalProcessor();
      break;
    case 'applePay':
      processor = new ApplePayProcessor();
      break;
    default:
      console.log('Invalid payment method.');
      return;
  }

  processor.processPayment(order);
  // ... 其他訂單處理邏輯 ...
}
```

在這個例子中，我們使用了物件導向的設計模式，將不同的支付方式抽象化為獨立的類別。這樣做的好處是：

*   **可擴充性：** 新增支付方式變得更加容易，只需要創建一個新的類別即可。
*   **可維護性：** 每個支付方式的邏輯都獨立存在，修改其中一個不會影響其他支付方式。
*   **可測試性：** 每個支付方式都可以獨立進行單元測試。

## 結論：持續投資，而非一次性革命

技術債不是髒話，而是一種需要管理的資源。成熟的工程師不會追求零技術債，而是有意識地管理它，把重構當作持續的投資，而非一次性的革命。透過量化技術債的成本與風險，並制定有效的償還策略，我們可以確保系統的長期健康和可維護性。身為 Tech Lead，你的職責是引導團隊建立這種意識，並將重構納入日常開發流程中。
